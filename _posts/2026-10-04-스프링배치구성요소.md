## 스프링 배치 핵심 구성 요소

#### Job
- Job은 하나의 완전한 배치 처리 작업이다.
- 하나 이상의 Step으로 구성된다.
- 여러 Step을 순서대로(또는 조건에 따라) 실행하도록 구성한다.
- Job 자체는 실행 흐름을 정의할 뿐 실제 처리 로직은 Step이 담당한다.
- `JobBuilder`를 통해 생성하며, `start()`로 시작 Step을 지정하고 `next()`로 다음 Step을 연결한다.

Job 구성 예시
```java
@Bean
public Job simpleJob(JobRepository jobRepository, Step step1, Step step2) {
    return new JobBuilder("simpleJob", jobRepository)
            .start(step1)
            .next(step2)
            .build();
}
```

#### Step
- Step은 Job의 세부 실행 단계이다. 
- 하나의 Step이라도 실패하면 그 즉시 Job 전체가 실패한다
- Step은 두 가지 방식이 존재한다.
    - Tasklet(테스클릿 지향 처리 - Task Oriented Processing)
    - ItemReader / ItemProcessor / ItemWriter (청크 지향 처리 - Chunk Oriented Processing)
- `StepBuilder`로 생성하며, `tasklet()` 또는 `chunk()`로 처리 방식을 지정한다.

Step 구성 예시
```java
@Bean
public Step step1(JobRepository jobRepository, PlatformTransactionManager transactionManager, Tasklet myTasklet) {
    return new StepBuilder("step1", jobRepository)
            .tasklet(myTasklet, transactionManager)
            .build();
}
```

#### Tasklet 방식
- 주로, 복잡하지 않은 단일 작업 수행에 사용한다.

Tasklet 예시
```java
public class MyTasklet implements Tasklet {
    @Override
    public RepeatStatus execute(StepContribution contribution, ChunkContext chunkContext) {
        // 단일 작업 수행
        return RepeatStatus.FINISHED;
    }
}
```
- Tasklet 인터페이스를 구현하며, execute() 메서드를 제공하고, 반환값은 RepeatStatus이다.
- RepeatStatus (반환값)
    - FINISHED: 해당 step 완료됐음을 의미하고 다음 Step으로 넘어간다.
    - CONTINUABLE: `execute()`를 재실행하며, Step 종료는 보류되고, 필요한 만큼 `execute()` 메서드가 반복호출된다.
- `execute()` 메서드 단위로 트랜잭션이 동작한다.
    - Step 구성 시 `PlatformTransactionManager`를 넘겨줘야 트랜잭션이 동작한다. (기본은 `ResourcelessTransactionManager`으로 NOP으로 동작)
    - `CONTINUABLE`를 반환해 `execute()` 메서드가 재실행되면, 별도의 트랜잭션에서 실행된다.

```
1. execute() 실행
2. TX 시작
3. 예외 발생
4. RepeatStatus.CONTINUABLE 반환
5. TX 롤백
6. execute() 재실행 → 다시 1번부터 반복
```

#### 청크 방식 (ItemReader / ItemProcessor / ItemWriter)
- 청크 방식 Step의 구성 요소
    - `ItemReader`: 데이터를 읽어 오는 컴포넌트
        - 아이템 하나(한 row)씩 반환한다.
        - null을 반환할 경우 더이상 읽을 데이터가 없다고 판단하여, Read를 종료한다.
        - 파일, CSV, DB 등 다양한 구현체를 제공한다.
    - `ItemProcessor`: 데이터를 가공하는 컴포넌트
        - reader에서 전달받은 아이템 가공하는 역할 (필수는 아니므로 생략가능)
        - null을 반환하면 해당 데이터는 제외된다.
        - 예외를 발생할 경우 Job 중단하는데, 설정에 따라 예외 데이터만 건너뛰기도 가능하다.
    - `ItemWriter`: 데이터를 저장하는 컴포넌트
        - Reader OR Processor가 만든 결과물을 받아, 원하는 방식으로 최종 출력한다.
        - 데이터를 한 건씩 쓰지 않고, 청크 단위로 묶어서 한 번에 데이터를 쓴다.
        - DB, 파일 등 다양한 구현체 제공한다.
- 청크 크기가 커밋 단위가 된다.
    - reader → (processor) 를 청크 크기만큼 반복한 뒤, writer가 한 번에 write() 하고 그 시점에 트랜잭션이 커밋된다.
    - 처리 중 예외가 발생하면 해당 청크 단위로 롤백된다.
    - Tasklet 방식은 execute() 단위로 트랜잭션이 묶이는 반면, 청크 방식은 청크(chunk) 단위로 트랜잭션이 묶인다는 차이가 있다.
- `faultTolerant()`를 통해 결함 허용(skip/retry) 정책을 설정할 수 있다.
    - skip: 특정 예외 발생 시 해당 아이템을 건너뛰고 계속 진행 (허용 횟수 지정 가능)
    - retry: 특정 예외 발생 시 해당 아이템 처리를 재시도 (재시도 횟수 지정 가능)

청크 방식 예시
- `chunk(10, transactionManager)`에서 10이 청크 크기(커밋 단위)이다.
```java
@Bean
public Step step1(JobRepository jobRepository, PlatformTransactionManager transactionManager,
                   ItemReader<Input> reader, ItemProcessor<Input, Output> processor, ItemWriter<Output> writer) {
    return new StepBuilder("step1", jobRepository)
            .<Input, Output>chunk(10, transactionManager)
            .reader(reader)
            .processor(processor)
            .writer(writer)
            .build();
}

public class MyItemReader implements ItemReader<Input> {
    @Override
    public Input read() {
        // 데이터를 하나씩 읽어서 반환, 더 이상 없으면 null 반환
        return ...;
    }
}

public class MyItemProcessor implements ItemProcessor<Input, Output> {
    @Override
    public Output process(Input item) {
        // item을 가공하여 반환, 제외하려면 null 반환
        return ...;
    }
}

public class MyItemWriter implements ItemWriter<Output> {
    @Override
    public void write(Chunk<? extends Output> chunk) {
        // 청크 단위로 모인 아이템들을 한 번에 저장
        for (Output item : chunk) {
            ...
        }
    }
}
```

## 스프링 배치 기타 구성요소

#### JobRepository
- Job/Step 실행과 관련된 메타데이터(JobInstance, JobExecution, StepExecution 등)를 DB에 저장하고 관리한다.

#### JobLauncher
- Job과 JobParameters를 받아 Job을 실행하는 객체.
- `jobLauncher.run(job, jobParameters)` 형태로 호출한다.
- Spring Batch 6.0부터 deprecated 되었고, `JobOperator`로 대체되었다.

JobLauncher 예시
```java
@Autowired private JobLauncher jobLauncher;
@Autowired private Job myJob;

public void run() throws Exception {
    JobParameters jobParameters = new JobParametersBuilder()
            .addLong("time", System.currentTimeMillis())
            .toJobParameters();
    jobLauncher.run(myJob, jobParameters);
}
```
#### JobParameters
- Job 실행 시 전달하는 입력값. 배치가 어떤 조건/데이터로 동작할지 결정하는 역할을 한다.
- `JobParametersBuilder`로 생성하며, String/Long/Double/Date 등 다양한 타입의 파라미터를 추가할 수 있다.
- JobInstance를 구분하는 기준이 된다. (파라미터 값이 다르면 같은 Job이라도 다른 JobInstance로 식별)
    - 단, `identifying` 파라미터만 식별 기준에 포함된다. (기본값은 true)
- JobRepository에 메타데이터로 저장되어, Job이 언제 어떤 파라미터로 실행됐는지 추적할 수 있다.

JobParameters 예시
```java
JobParameters jobParameters = new JobParametersBuilder()
        .addString("name", "kmin", true)   // identifying 파라미터 (기본값, 생략 가능)
        .addLong("time", System.currentTimeMillis(), false)  // non-identifying 파라미터
        .toJobParameters();
```

JobParameters 사용 예시 (Step/Tasklet에서 꺼내 쓰기)
1. `@Value("#{jobParameters['key']}")` 방식은 Job 실행 시점에 값이 바인딩되어야 하므로, 반드시 `@StepScope`(또는 `@JobScope`)여야 한다.
    - `@StepScope`는 빈의 생명주기가 Step인 빈을 정의할 때 사용.
    - `@JobScope`는 빈의 생명주기가 Job인 빈을 정의할 때 사용.
2. ChunkContext에 파라미터를 직접 꺼내서 사용할 수 있다.
```java
// 1. @Value + SpEL로 주입받기 (Step 범위 빈이어야 함)
@Bean
@StepScope
public Tasklet myTasklet(@Value("#{jobParameters['name']}") String name) {
    return (contribution, chunkContext) -> {
        System.out.println(name);
        return RepeatStatus.FINISHED;
    };
}

// 2. ChunkContext를 통해 직접 꺼내기
public class MyTasklet implements Tasklet {
    @Override
    public RepeatStatus execute(StepContribution contribution, ChunkContext chunkContext) {
        String name = (String) chunkContext.getStepContext()
                .getJobParameters()
                .get("name");
        return RepeatStatus.FINISHED;
    }
}
```

#### JobParametersValidator
- JobParameters 값이 유효한지 검증하는 역할.
- `JobParametersValidator` 인터페이스를 구현하며, `validate(JobParameters)` 메서드를 제공한다. 
- 유효하지 않으면 `JobParametersInvalidException`을 던져 Job 실행 자체를 막는다.
- 스프링 배치가 기본 제공하는 `DefaultJobParametersValidator`로 필수/선택 파라미터 키만 간단히 지정할 수도 있다.
- `JobBuilder`의 `validator()`로 등록한다.

JobParametersValidator 예시
```java
public class MyJobParametersValidator implements JobParametersValidator {
    @Override
    public void validate(JobParameters parameters) throws JobParametersInvalidException {
        if (parameters.getString("name") == null) {
            throw new JobParametersInvalidException("name 파라미터가 필요합니다.");
        }
    }
}

@Bean
public Job simpleJob(JobRepository jobRepository, Step step1) {
    return new JobBuilder("simpleJob", jobRepository)
            .validator(new MyJobParametersValidator())
            .start(step1)
            .build();
}
```

#### JobInstance
- Job + JobParameters(identifying 파라미터만)로 식별되는 논리적인 실행 단위.
- 같은 Job이라도 JobParameters가 다르면 서로 다른 JobInstance로 취급된다.
- 이미 성공적으로 완료된 JobInstance를 동일한 파라미터로 다시 실행하면 `JobInstanceAlreadyCompleteException`이 발생한다. (재실행하려면 파라미터를 다르게 줘야 함)
- 실패한 JobInstance는 동일한 파라미터로 재시작할 수 있으며, 이 경우 같은 JobInstance에 새로운 JobExecution이 추가된다.

#### JobExecution
- JobInstance의 1회 실행을 나타내는 객체.
- JobInstance(1) - JobExecution(N) 구조. (같은 JobInstance라도 재시작하면 새로운 JobExecution이 생성된다.)
- 실행 상태(`BatchStatus`: STARTED/COMPLETED/FAILED 등)와 종료 상태(`ExitStatus`), 시작/종료 시간, 해당 실행에 속한 StepExecution 목록 등을 가지고 있다.
- `jobLauncher.run()`의 반환값으로 받을 수 있으며, 이를 통해 실행 결과를 바로 확인할 수 있다.

```java
JobExecution jobExecution = jobLauncher.run(myJob, jobParameters);
BatchStatus status = jobExecution.getStatus();  // COMPLETED, FAILED 등
```

#### StepExecution
- Step의 1회 실행을 나타내는 객체.
- JobExecution(1) - StepExecution(N) 구조.
- Step이 실패하면 이후 Step은 실행되지 않으므로, 실패 지점 이후의 StepExecution은 생성되지 않는다.
- 실행 상태(`BatchStatus`)와 종료 상태(`ExitStatus`)를 가지며, read/write/skip count 등 처리 건수 정보도 담고 있다.
- Tasklet의 `execute()` 파라미터(`ChunkContext`)를 통해 접근할 수 있다.

```java
@Override
public RepeatStatus execute(StepContribution contribution, ChunkContext chunkContext) {
    StepExecution stepExecution = chunkContext.getStepContext().getStepExecution();
    long readCount = stepExecution.getReadCount();
    return RepeatStatus.FINISHED;
}
```

#### JobExecutionListener
- Job 실행의 시작 전 / 종료 후에 호출되는 리스너 인터페이스

```java
public class MyJobExecutionListener implements JobExecutionListener {
    @Override
    public void beforeJob(JobExecution jobExecution) { ... }

    @Override
    public void afterJob(JobExecution jobExecution) { ... }
}
```

#### StepExecutionListener
- Step 실행의 시작 전 / 종료 시점에 호출되는 리스너
- `beforeStep()`
    - Step의 시작 시점(정확히는 StepScope 활성화된 직후)
- `afterStep()`
    - Step 종료시점에 호출
    - ExitStatus를 반환해 Step의 종료 상태를 변경할 수 있다.

```java
public class MyStepExecutionListener implements StepExecutionListener {
    @Override
    public void beforeStep(StepExecution stepExecution) { ... }

    @Override
    public ExitStatus afterStep(StepExecution stepExecution) {
        return stepExecution.getExitStatus();
    }
}
```

#### ChunkListener
- 청크 단위로 동작을 반복한다.
- `beforeChunk()`
    - `ItemReader`가 청크 크기만큼 아이템을 읽은 직후 `ItemProcessor`가 처리를 시작하기 전에 호출된다.
- `afterChunk()`
    - `ItemWriter` 완료 후 트랜잭션인 커밋되기 전에 호출된다.
    - 청크 처리 중 예외가 발생하면 호출되지 않는다.
- `onChunkError()`
  - reader / processor / writer 처리 중 예외가 발생하면 호출
  - 트랜잭션 롤백 전이므로 이 메서드 내에서 트랜잭션 작업이 필요하다면, `PROPAGATION_REQUIRES_NEW`를 사용해야 함.
  - 두 번째 파라미터 Chunk<O>는 ItemProcessor가 처리를 완료한 아이템을 담고 있다.
      - 즉, ItemReader에서 발생 시 청크가 비어있다.

```java
public class MyChunkListener implements ChunkListener {
    @Override
    public void beforeChunk(ChunkContext context) { ... }

    @Override
    public void afterChunk(ChunkContext context) { ... }

    @Override
    public void afterChunkError(ChunkContext context) { ... }
}
```

#### Item[Read/Process/Write]Listener
- read / process /write 각 작업 실행 전/후 예외 발생 시 호출된다.

```java
public class MyItemProcessListener implements ItemProcessListener<Input, Output> {
    @Override
    public void beforeProcess(Input item) { ... }

    @Override
    public void afterProcess(Input item, Output result) { ... }

    @Override
    public void onProcessError(Input item, Exception e) { ... }
}
```
